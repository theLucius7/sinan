# ADR 0028：共用诊断任务服务

状态：采用。对应 Issue #27。

## 决定

面板的 `diagnostics` 服务统一负责设备能力及签名制品检查、创建任务、资源预算、同机互斥、持久化、确认式取消、结果上传、章节完整度和历史记录。Agent 继续使用已有的诊断 worker、SQLite checkpoint/outbox、独立系统服务和资源预检；插件不得另起任务存储、另写设备连接或单独控制生命周期。

登记表只包含编译进面板的插件。每个插件提供标识、工具版本、所需能力、参数转换得到的诊断计划，以及报告链接解析规则。参数转换可以读取已有的目标配置和运行时活动证据，不能写诊断任务表。执行及报告解析仍在具体 Agent 适配器中。第一个迁移对象为 NodeQuality；确认队列、恢复及历史报告测试通过后，才登记第二个插件。

通用管理员入口为 `GET /api/servers/{id}/diagnostics` 和 `POST /api/servers/{id}/diagnostics/{plugin}`。既有 NodeQuality 路由继续调用同一个服务，历史记录原表、ID、JSON、整份报告及章节均不迁移、不删改。插件页面只读取自己的历史，通用历史可以展示已停用插件的既有记录。

## 预算与兼容

`DiagnosticJob.resource_budget` 是可空的增量字段。新任务由登记的计划填写 MemoryMax、TasksMax、CPUWeight、IOWeight、OOMScoreAdjust，并保存到原有 JSON。面板不能从请求接收任意预算或任意命令。设备必须声明 `diagnostic:job-service` 才会接收新任务，避免旧 Agent 忽略预算字段。

2026-10-03 扩展 CPU 带宽硬上限：`cpu_max_percent` 是可选增量字段，范围1–6400，100%表示一个逻辑核的总运行时间，200%表示两个逻辑核，不按整机百分比解释。CPUWeight 仍只表示资源竞争权重。缺少该字段的旧任务不改变适配器限制；缺少 SDK 新字段的旧配置采用100%的保守默认，新任务只能收紧适配器上限。面板新建诊断同时要求 `diagnostic:cpu-quota:v1`，旧 Agent 的已有报告与未知启动恢复保持原生命周期，不能用新默认值追认旧进程已受硬上限保护。

实际执行要求 Linux systemd/cgroup v2 CPU 控制器。启动前有界查询控制器，systemd 设置 `CPUQuota` 与100ms周期；固定 `ExecStartPre` 在目标控制组读取实际 `cpu.max`，只有有限正值且不超过请求上限才允许测试程序启动。不可读取、不支持、无限制或被放宽时拒绝执行，不降级为 CPUWeight。运行环境报告分别记录硬上限配置与竞争权重；新增测试覆盖实际前置检查程序对超限、无限制、缺失和无效值的拒绝，真实控制组验收仍需符合条件的 systemd 设备。

core 使用 `cpu_ceiling` 命名；边界检查器仅为上述 systemd 属性赋值与测试中的精确属性读取表达式增加窄例外，不能由此引用代理业务额度模型。CPU 与 seccomp 条件组合在同一条固定 `ExecStartPre`，保留原系统调用保护，不依赖重复前置命令赋值的覆盖行为。

Agent 验证预算范围后，在资源预检与启动 checkpoint 之前应用；只能收紧适配器准备的限制，不能增大内存/进程/争抢权重或降低 OOM 被回收优先度。资源范围检查不代替可用内存、磁盘、负载及本机服务检查。没有新预算字段的旧签名任务继续使用适配器原有预算恢复，不重复执行不确定的启动。Linux 后端的实际约束能力沿用既有系统服务实现，预算字段不宣称其他系统具备 systemd cgroup 限制。

创建持有服务器行锁，互斥查询覆盖同一服务器的全部插件，以及等待取消确认的任务。任务超时、失败或完整度变化不能伪造设备确认取消。取消仍经过共用协议、持久请求、停止服务、进程及挂载检查、设备确认流程；登记第二个插件时无需复制这套流程。

## 验收

旧/新创建路由竞争只产生一个任务；另一插件的活动记录阻止创建；缺失能力和未登记插件被拒绝；不接受管理员自定义预算；旧 r2 历史原文与失败任务的已完成章节仍可读。协议覆盖空预算兼容；Agent 覆盖不可放宽本地限制、拒绝预算不改变服务、无效计划不下载制品，以及已有离线、重启、过期和取消测试。

制品运行时下载链的固定与签名是 Issue #28 的独立整改，此次抽象不把入口脚本固定当作整条链固定。
